# VELA-X — קושחת שער העמדה

קושחת ESP32 שמגשרת בין הענן למכונת PUSUN PT-9001.

---

## מה זה, ומה זה לא

**זה לא חלק מאפליקציית הטלפון.** זו קושחה משובצת (C++/Arduino) שרצה על
מכשיר נפרד המותקן בעמדה.

השער והאפליקציה הם **שני לקוחות עצמאיים של אותו שרת**. הם אינם מדברים זה
עם זה:

```
אפליקציה  ──→  /api/app/v1/*      ──┐
                                     ├──→  שרת VELA-X
שער בעמדה ──→  /api/gateway/v1/*   ──┘
```

⚠ **נקודת התיאום היחידה היא ה־BLE.** מודול המכונה הוא `slave` ומקבל
**חיבור אחד בלבד**. אם השער מחזיק את החיבור, האפליקציה לא תוכל להתחבר.
זו ההחלטה בין מסלול א׳ ל־ב׳ — ראה `../REMOTE_CONTROL.md`.

---

## למה השער קיים

ל־PT-9001 אין WiFi ואין סלולר. הערוץ היחיד הוא BLE בטווח כעשרה מטרים,
ולכן הענן אינו יכול להגיע אליה. עד היום הטלפון היה הגשר — ומכאן שנדרש
אדם בשטח לכל פעולה. השער מחליף אותו ומאפשר שליטה מרחוק אמיתית.

---

## חומרה

| רכיב | הערה |
|---|---|
| ESP32 (DevKit v1 או דומה) | BLE + WiFi מובנים, 30–60 ₪ |
| ספק כוח 5V | קיים בעמדה — המכונות נטענות |
| מארז | עמידות לתנאי המקום |

מיקום: בטווח BLE מהמכונה (עד ~10 מטר, פחות דרך קירות) ובקליטת רשת המועדון.

## הרכבה

```bash
cd gateway-firmware
# ערוך src/config.h — רשת, מפתח שער, כתובת שרת
pio run --target upload
pio device monitor
```

### `src/config.h`

```c
#define WIFI_SSID      "CLUB-WIFI"
#define WIFI_PASSWORD  "..."
#define API_BASE       "https://velax-ops-console.netlify.app"
#define GATEWAY_KEY    "<מפתח מהקונסולה>"
```

⚠ **המפתח מוצג פעם אחת** ברישום השער בקונסולה, ואינו ניתן לשחזור. אם אבד
— סבב מפתח בקונסולה והזנה מחדש כאן. זו התנהגות מכוונת: מפתח שאפשר לשלוף
מהמסד הוא מפתח שדליפת מסד חושפת.

## מבנה

| קובץ | תפקיד |
|---|---|
| `src/pusun_protocol.h` | קידוד ופענוח פרוטוקול המכונה |
| `src/main.cpp` | לולאת WiFi, BLE, ותקשורת עם השרת |
| `src/config.h` | הגדרות מקומיות |

### `pusun_protocol.h`

⚠ **חייב להישאר תואם ל־`src/lib/pusun/protocol.ts` בשרת.** שם קיימות 23
בדיקות מול כל דוגמאות היצרן. אומת שהקידוד כאן זהה בית־בבית — כולל בית
הביקורת ב־notify, שהמסמך מכנה `DEFAULT` ואינו מתעד שהוא `COMMAND XOR DATA1`.

---

## הלולאה

```
כל 3 שניות:   GET  /api/gateway/v1/commands   →  שידור BLE  →  POST תוצאה
כל 60 שניות:  POST /api/gateway/v1/telemetry
```

⚠ **מסגרות ה־notify נשלחות גולמיות.** הפענוח נעשה בשרת, כדי שיהיה מקור
אמת אחד לפרוטוקול ותיקון באג לא ידרוש עדכון קושחה בכל העמדות.

---

## מיפוי פקודות

| פקודה מהשרת | פרוטוקול המכונה |
|---|---|
| `stop`, `force_stop` | `0x6B` |
| `pause` | `0x6B` — ⚠ אין השהיה בפרוטוקול; חידוש מתחיל מחדש |
| `start`, `resume` | `0x66` צפצוף, ואז `0x6A` עם מצב ההגשה |
| `apply_settings` | `0x63` מהירות, `0x61` תדירות, `0x62` סיבוב |
| `ping` | `0x67` בקשת סוללה |
| `lock`, `unlock` | ❌ **אינן קיימות בפרוטוקול** — מדווח ככישלון |

⚠ פקודה שאין לה מקבילה מדווחת ככישלון מפורש ולא כהצלחה. אישור שקרי גרוע
מכישלון: הוא גורם לקונסולה להציג שהמכונה צייתה.

⚠ גם היעדר חיבור BLE מדווח ככישלון ולא נבלע בשקט, כדי שהמפעיל יראה
שהפקודה לא בוצעה.

## בדיקה לפני התקנה בשטח

1. `pio device monitor` — לוודא WiFi, ואז `[BLE] מחובר למכונה`
2. בקונסולה: מסך הסשן → "עצור" → הפקודה נכנסת לתור
3. תוך שלוש שניות המכונה עוצרת, והפקודה עוברת ל`acknowledged`
4. מסך בקרת השימוש מתחיל לקבל קריאות סוללה רציפות

---

## מה שנשאר פתוח

- **HTTPS**: `HTTPClient` כאן ללא הצמדת תעודה. לפני פריסה רחבה מומלץ
  להצמיד את תעודת השרת (certificate pinning).
- **OTA**: אין עדכון קושחה מרחוק. עדכון מצריך גישה פיזית.
- **חיבור מרובה**: המודול מקבל חיבור אחד; מצב `HOLD_ALWAYS` חוסם את
  האפליקציה. ראה `../REMOTE_CONTROL.md`.
